# P0.2.1 — user-driven tie correction and optional music check

1. **Files changed in this milestone.** Application files: `backend/app/api/v1/reviews.py`, `backend/app/music/review/ties.py`, `backend/app/music/review/service.py`, `backend/app/music/review/confirmations.py`, new `backend/app/music/review/music_check.py`; `frontend/src/components/RecognitionReview.tsx`, `ScoreCorrectionToolbar.tsx`, `EventInspector.tsx`, `frontend/src/services/api.ts`, `frontend/src/types/review.ts`, `frontend/src/utils/visualReview.ts`. Tests: new `backend/tests/test_p021_user_ties.py`, new `frontend/tests/user-ties-check.test.mjs`; existing backend tests `test_review_existing_ties.py`, `test_review_tied_insertion.py`, `test_p0_scanner_editor.py`, `test_phase4e_workflow.py`, `test_phase4f_lyrics.py`, `test_phase4f_structure.py`, `test_review_overfill_diagnosis.py`, `test_semantic_recovery.py`; frontend tests `review-insertion.test.mjs`, `review-workspace.test.mjs`, `visual-review.test.mjs`. This report is new. Existing uncommitted work was preserved. Old tests asserting mandatory theory gates were updated to the explicitly requested advisory policy; their preservation/history assertions remain.
2. **Why Tie was disabled.** The toolbar required a backend target other than the current target and rejected grace notes. Backend candidates required matching pitch/voice/staff, adjacent time, no intervening events and this/next measure ownership. These theory restrictions could yield no selectable target even when a user saw a tie in the source.
3. **Previous duplicate behavior.** The patcher counted starts/stops and rejected any repeated endpoint with “Duplicate tie endpoints require repair in a notation editor.” It did not compare attributes or distinguish identical duplication from different numbered, repeat-scoped or formatted markings.
4. **Previous validation architecture.** One combined projection carried technical import errors, rhythm checks and manual-tie checks. Manual-tie conventional incompatibility was ERROR; overfill/overlap could block Verify. Scoped source confirmation waived selected rhythm findings, but not tie incompatibility. The old Validate action advanced the session revision.
5. **New normal workflow.** Select source note → Tie → source remains selected and Tie mode shows guidance/highlighted targets → explicitly click target → one relationship-only PATCH → canonical XML response rerenders. Cancel tie/Select exits without editing. No alternate target is chosen automatically. Existing targets remain selectable so the user can explicitly correct identical duplicated markup.
6. **Source endpoint.** `tieSource` retains the selected canonical ID through target selection. Backend source capability is exposed as `tie_correction_error`, with a technical explanation when unavailable. Grace notes can be tied; Small display does not become cue semantics. OSMD stays the renderer/hit adapter; it is not the score database.
7. **Target endpoint.** Candidates are technically supported pitched notes anywhere in the same part, including different voices/staves, pitches and nonadjacent/earlier times. Target capture uses existing uniquely mapped notehead selection. The submitted target ID is the user's choice. A known incoming relationship cannot be stolen; stale revision/identity fails atomically.
8. **Canonical relationship.** Existing XML-bound `manual_ties[sourceId]` stores the explicit target and ownership/cleanup metadata, with optional MusicXML tie number. One outgoing and one incoming relationship per event remain the bounded editable model; incoming/outgoing continuation sides remain separate. No generic relationship-engine redesign.
9. **MusicXML patch.** The existing cloned-document preservation path adds sound `<tie>` and visual `<tied>` start/stop endpoints only. Neither pitch, onset, duration, staff/voice, notes, lyrics, accidentals nor neighboring events are changed by a tie-only PATCH. Nonconventional pairs receive an unused visual `tied@number` on the chosen endpoints; default number 1 is reserved for conventional unnumbered ties. Conventional creation does not require an unused number. Namespaces and unrelated XML are retained.
10. **Exact duplicates.** On an explicit edit of the chosen relationship, identical endpoint elements are compared by attributes/content, ignoring attribute order and indentation. Only repeated copies at the selected start/stop are removed; the first marking and its attributes remain. Import and Check do not normalize XML. Repeating an already-identical link returns an explanatory no-change response (422) and adds no duplicate or history entry. Distinct attributes/numbers/repeat scopes are preserved and not treated as identical duplicates.
11. **Stale endpoints.** Missing source/target, stale If-Match revision, or a dangling internal target produces a controlled error and no committed partial patch. Missing internal target data is reported as technical integrity failure. An unresolved imported start can be explicitly bound by choosing its target; no unrelated orphan stop is removed. Removing an unresolved relationship requires identifying its target first.
12. **Same-pitch policy.** Conventional same-*sounding*-pitch is advisory, including enharmonic equivalence. A differing-pitch correction is accepted without pitch substitution; `tie_pitch_mismatch` is a MUSIC_WARNING. Different voices/staves and nonconventional timing are also advisory. MusicXML distinguishes sound ties and visual ties, and provides visual tie numbering; different-pitch notation is discouraged by the specification, rather than forbidden by its element structure. References: [MusicXML tied](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/tied/), [tie](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/tie/), [number-level](https://www.w3.org/2021/06/musicxml40/musicxml-reference/data-types/number-level/).
13. **What blocks correction.** Missing/stale identity, self/cross-part connection outside this part-scoped model, malformed pitched-note/duration/voice/staff state, explicit cue semantics incompatible with this sound-plus-notation command, incoming relationship ownership, distinct markings the single-relationship editor cannot distinguish, invalid tie numbering, unavailable unambiguous numbering for a nonconventional pair, and existing quota/storage integrity checks. These are bounded representation/capability constraints; no musical rule is disguised as an error.
14. **Warning-only findings.** Tie pitch mismatch, voice/staff differences, nonconventional timing, unresolved imported ties, repeated/distinct endpoint markings, meter underfill/overfill/mismatch, voice overlap, unusual chord duration, complex/unknown meter and empty measures are advisory. Invalid pitch/duration/timing/part/staff/note-kind data, invalid tie type/number markup and missing manual endpoint markup remain technical. Whole-score absence of musical events remains a technical inability to verify/transpose.
15. **Optional Check architecture.** `music_check.py` classifies existing diagnostics as MUSIC_WARNING, TECHNICAL_ERROR or INFORMATION. Recognizer/recovery behavior is unchanged. The existing projection still supplies integrity/capability data during editing; displaying musical assistance is opt-in. `POST /reviews/{id}/music-check` requires current If-Match and returns diagnostic findings/counts for that revision. It writes no XML, sidecars, session state, revision, undo/redo entry or verification decision. Existing `/validate` remains a compatibility endpoint; the optional UI does not call it.
16. **Optional Check UI.** “Optional music check” offers “Check score.” Before invoking it, musical warnings are not forced into the correction panel. Technical findings remain available separately. Check has its own API/result flow and never calls correction `onChange`, so it cannot discard a verified master or transposed preview. Results carry the checked revision; stale results are hidden with a rerun message. Errors/expiry retain existing score-download behavior.
17. **Verify/source comparison.** Music warnings do not require Check or per-warning approval before Verify. Explicit whole-score source comparison and existing recognition-issue handling remain required. Technical errors still block. Optional scoped “This unusual notation matches the source” confirmations reuse fingerprints, revision invalidation and undoable sidecars; they do not waive technical failures or rewrite XML. Successful correction still invalidates verification/transposition through the accepted lifecycle.
18. **Remove Tie.** Explicit null removes the identified outgoing start and its corresponding target stop only, preserving the source's incoming stop, target's outgoing start, unrelated ties, slurs, lyrics, accidentals and all note data. Distinct ambiguous markings are not bulk-deleted. Namespace/continuation regressions and a two-relationship removal test cover this.
19. **Undo/Redo.** Tie creation, change, explicit duplicate correction and removal use the existing atomic document/sidecar snapshots. One completed operation creates one history entry. Tests restore exact prior XML for creation/removal Undo and Redo; failed, cancelled, repeated-identical and Check operations create no history operation.
20. **P0.2 drag.** No drag module, renderer binding, viewport/coordinate adapter or drag tests were changed. All 15 focused drag tests pass: 5px threshold, vertical-only same-event pitch, clef/staff geometry, Fit/zoom, anchored preview, one edit, unsafe cancellation and history. Tie mode continues to disable pitch dragging through the existing tie-target-mode boundary.
21. **P0.1/source regressions.** Note-value symbols, accidental add/clear, NONE versus Natural, Follow key context, lyric Add/Edit/Delete, Unicode/multiple verses and size/timing remain covered. The accepted source-system renderer and layout algorithm were not edited. Source immutability, grouping, Fit/zoom, selection/insertion, Corrected/Transposed switching, XML preservation and absolute verified-master transposition tests pass.
22. **Frontend validation.** `node --test tests/*.test.mjs`: all **10 test files pass**. New tie/check file: **9 focused cases**. Advanced insertion coverage also verifies grace-note tying while retaining rest/technical restrictions. Existing frontend regression files remain passing.
23. **Backend validation.** Full suite: **705 passed**, with two existing test-client deprecation warnings. New focused file contains 22 cases. Command from backend: `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONPATH=. .venv/bin/pytest -q`. Tests run outside the sandbox because the established TestClient harness stalls in it. Plugin autoload remains disabled for an unrelated installed ROS plugin dependency. No recognition provider or browser acceptance was run.
24. **Lint.** `npm run lint` passes.
25. **Build.** `npm run build` passes (TypeScript and Vite); the existing large bundle warning remains.
26. **Whitespace.** `git diff --check` passes. New implementation/test/report files were additionally checked with `git diff --no-index --check /dev/null <file>`; no whitespace errors.
27. **Known limitations/manual acceptance.** Editing is part-scoped and supports one incoming/outgoing pair per event. It cannot choose among distinct same-direction numbered/repeat/format markings; those are preserved, explained and surfaced for optional review. Nonconventional pairing uses globally unused numbers 2–16 in its part and does not attempt number reuse or endpoint inference. Legacy unnumbered imported relationships resolve only a unique conventional pair; ambiguity requires user selection. Numbered nonconventional export/re-import preserves chosen endpoints in application tests, but OSMD and external consumers may render/play unusual ties differently or ignore them. Only the first relevant conventional discrepancy per link is reported; no larger theory engine is built. ## Browser Acceptance Failure and Fix

This section supersedes the earlier tie eligibility, single-incoming ownership, duplicate/replay and rendering limitations in items 5–13, 18, 20, 22–23 and 27. Those items record the initial implementation, whose automated results did not establish browser acceptance.

**Diagnostic evidence collected before changing behavior.** Added tests first, then ran them against the failing implementation. Two representative backend cases reproduce distinct numbered/placed start fragments at notes labelled “Mừng” and “Trời”; both failed because `tie_correction_error` contained the distinct-markings rejection. A third backend case containing recognized start/stop fragments failed with HTTP 422 and “This relationship is already connected.” Two frontend regressions failed because an editable source with an empty candidate list/distinct-markup error could not start Tie, and selecting a real target absent from that list emitted no PATCH. Lyrics appear only in diagnostic test fixtures, never in production eligibility logic. The closest fixture is the preservation-rich MusicXML in `test_review_existing_ties.py`, used by the existing review-session/TestClient architecture. The actual “Đem Tin Mừng” browser sessions and their XML are not present in this workspace; therefore these reproductions identify the exact faulty code paths, not the precise saved fragment set at either actual benchmark note.

**Why button states differed.** `ScoreCorrectionToolbar.tsx` previously disabled Tie through `!tying && (!!event?.tie_correction_error || !event?.tie_target_ids?.length)`. Backend `tie_info()` called `endpoint_safe()` on the source, which rejected multiple distinct signatures. `targets()` also checked both endpoints and incoming relationships inferred from raw XML; those filters could empty the candidate list. Consequently distinct fragments or an empty precomputed list muted Tie before target selection. Another selected note with no such error and at least one remaining candidate enabled it. `RecognitionReview.selectEvent()` then accepted only IDs in `source.tie_target_ids`; this was an additional silent filter after entering Tie mode.

**Why “already connected” appeared.** `set_target()` previously obtained `old_target` from `current_target()`, which inferred a target from numbered or conventional raw fragments. If the user's target equalled that inferred ID and no identical nodes needed deduplication, it rejected the correction as already connected. Neither an explicit canonical correction nor a correctly rendered curve had been established. This inference is now confined to recognized/imported information and legacy uniquely resolved removal; it never decides whether an explicit A→B creation is redundant.

**Separate representations.** Raw `ties`/recognized `tie_target_id` remain recognition evidence. `document.manual_ties` and the projected `tie_relationship` describe the explicit canonical source/target, owned XML identities and origin. New authoring has `USER_CORRECTION` origin; uniquely paired exported correction identities can be restored with `EXPORTED_CORRECTION` origin, without claiming a fresh source comparison. Arbitrary scanner markers, duplicated identities across distinct notes, mismatched numbers and cross-part pairs are not promoted by that restoration. Visible SVG correction curves are a separate viewing layer derived only from canonical relationships. Whole-score user confirmation remains the existing revision-bound source-comparison decision.

**New user workflow.** A selected editable pitched note can start Tie without any precomputed candidate. An explicit backend `tie_source_editable: false` disables it only for the supported command's technical limitations, with the exact reason displayed. Raw distinct/duplicate markings do not set that flag. Target highlights come from real note identities rather than inferred candidate eligibility; the next selected distinct real note supplies the exact target to one PATCH. Backend validates identities and the bounded same-part representation. Pitch, voice/staff differences, nonadjacency and meter remain optional advisory findings. No endpoint substitution, musical property change or automatic source confirmation occurs.

**Owned authoring, preservation and duplicate handling.** Every newly authored pair receives its own unused `tied@number` and unique standard `tied@id` values, independent of review event IDs. Existing distinct visual attributes, repeat scopes, incoming/outgoing sides, other notes, slurs, lyrics, layout data and comments are retained. Existing sound markers are reused; new ones carry ownership metadata. Only exact duplicate signatures at the explicitly edited start/stop are collapsed. An intact canonical repeat returns successful unchanged revision/XML/history, without the misleading rejection or frontend lifecycle invalidation. Missing or inconsistent owned visual endpoints cause a repair operation instead of a false no-op. One source has one outgoing canonical relationship; another incoming canonical relationship at the chosen target is preserved rather than blocking the new explicit choice.

**Removal and history.** Remove A→B deletes its owned visual IDs and only the sound nodes it introduced. Reused scanner markers remain. When two canonical relationships share a sound stop, removal transfers ownership to the remaining relationship; export/re-import preserves that ownership. Creation, retargeting, repair, duplicate cleanup and removal use one existing atomic snapshot operation each. Undo/Redo restore exact XML and sidecars. Stale requests and exact serialization conflicts fail without committing a candidate. Legacy imported removal still requires a uniquely resolved relationship; unresolved fragments must first receive an explicit target.

**Visible correction and renderer boundaries.** `scoreTies.ts` draws selectable blue curves between uniquely mapped canonical noteheads using inverse SVG screen coordinates, with endpoint continuation segments across pages/system wraps. Selecting a curve selects its source for Remove/retarget. A viewing clone suppresses only the pair's owned native `<tied>` nodes, avoiding a second native copy of the authored curve; unrelated scanner markers remain visible. The canonical/download XML is unchanged by viewing. Curve bindings are disposed on rerender and rebuilt on resize. The accepted source-layout code (`scoreRenderer.ts`, `sourceEngraving.ts`), source grouping/width algorithm and `pitchDrag.ts` were not edited. The interaction adapter gains curve binding; existing drag test mocks gain that dependency. The read-only Transposed viewer retains its native rendering path.

**Optional Check and regressions.** Check score remains a separate read-only request/result flow. Tests cover unchanged XML, revision, sequence, Undo/Redo, VERIFIED state and frontend `onChange`/transposed lifecycle. Existing P0.2 threshold/vertical drag/identity/zoom, P0.1 note values/accidentals/Unicode lyrics, source grouping/Fit, Corrected/Transposed switching, XML preservation and verification regressions pass. Older tests that required distinct-marking rejection, candidate filtering or an incoming-target blockade were updated to the authoritative policy while retaining preservation and history assertions.

**Final automated validation.** Focused backend tie suite: **68 passed**. Full backend suite: **711 passed**, with two existing TestClient deprecation warnings. All **11 frontend test files**, **133 cases**, pass, including canonical-only curves, zoom coordinates, continuation segments, cleanup, viewing-clone preservation, technical-source explanations and unchanged-revision replay. `npm run lint`, `npm run build` and `git diff --check` pass; the existing Vite large-bundle warning remains. Backend and Node test workers ran outside the sandbox because their established harnesses do not run/report reliably inside it. Backend plugin autoload stayed disabled for the unrelated installed ROS plugin.

**Known limits and acceptance status.** The command remains part-scoped, with one outgoing canonical relationship per source and the existing pitched-note/voice/staff/duration integrity and cue restrictions. Explicit numbers 2–16 are allocated without interval-based reuse; exhaustion now reports the exact occupied-number conflict instead of a generic ambiguity rejection. Distinct recognized markers may remain visible beside the blue correction because they are deliberately preserved. Curve placement is a viewing overlay, not a collision-aware engraving engine; shared/unmapped noteheads cannot receive a guessed curve, and unusual multi-system/staff/page relationships need visual inspection. External consumers and the native Transposed view may interpret unconventional ties differently. The actual benchmark still requires real-browser acceptance. **No browser acceptance is claimed.** No reset, restore, clean, stash, discard, staging, commit or push was performed. Work stops after implementation and automated validation.
